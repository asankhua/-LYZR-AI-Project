## What to do

### 1. Explore

Take reference from these platforms:

- [architect.new](https://architect.new) — the platform you will be building the next version of
- Replit
- Lovable
- Emergent
- Vercel v0
- Rocket.new
- Cursor
- Codex
- Claude Code
- or any other coding agent / vibe-coding platform

Understand every feature of each one:

- What makes each one different?
- Why are people using it?
- What features does each platform have?
- The UI, the UX, the user flows — everything

### 2. Build

Build **Architect 2.0**: a vibe-coding platform for both technical and non-technical users, where a user can:

- Build an entire agentic application just by prompting
- Import an existing project and keep working on it in Architect
- Build agents in any framework
- Connect GitHub to their app
- Deploy the app
- …and anything else you think it needs

Keep in mind:

- Architect 2.0 should have **all the features of the current Architect**. Today's Architect only caters to non-technical folks. The new version should also cater to technical folks (developers). Think about what additional features it needs to serve both audiences.
- Focus more on the **UI/UX and the flow of the entire app**, from authentication to deploying the app, and how every feature flow would look for the user.
- All the features you're adding don't need to be fully functional. You can create **dummy flows** to show how the user flow would look for each feature.
- If you can make some basic functionality work (authentication, database), that's a plus point. Otherwise dummy flows are good enough.

**Do not copy** the current Architect UI/UX, or any other platform's. Design from first principles: start from what the user needs, then design the flow. If you think of something better, or want to experiment, go for it.

### 3. Ship

Deploy it and share:

- The **live URL** with all major features in place
- The **GitHub repo**

Submit both in the **Submit** tab on [https://hiring.lyzrarchitect.space](https://hiring.lyzrarchitect.space).

## How they judge (in order of importance)

### 1. Design, UI/UX & flows — most important

Good design and product sense are a must. Think through everything from the user's perspective, down to the small things: where each button sits, which pages and sections exist, the layout, and how one step leads to the next.

### 2. Feature coverage — high

Cover every feature a platform like this needs. Dummy flows are fine, as long as each one shows product thinking and design.

Example surfaces (not a complete list):

1. Authentication
2. Homepage
3. Chat window
4. App preview
5. Agent section
6. UI getting built
7. GitHub integration
8. Deploying the app
9. Anything else technical and non-technical users would need

Don't stop at this list. Think holistically: what would technical folks need, and what would non-technical folks need?

### 3. Working functionality — plus points

Not required. Making a few basic things work (database, Google sign-in) earns plus points. This tests technical capability and how many things you can actually make functional.

## Current Architect features to cover

Architect 2.0 should include all of today's Architect capabilities, then add developer-facing ones. From [docs.architect.new](https://docs.architect.new):

- AI Consultant (role, bottlenecks, tools → app ideas)
- Prompt box with attach: files/RAG, theme, Studio agents, prompt library
- Plan / PRD, then agents + tools + knowledge bases, then UI
- Live preview, chat iteration, Plan Mode
- Themes (presets + bring-your-own from Figma / PDF / GitHub / zip)
- Managed database + auth (sign in/up, sessions, collections viewer)
- GitHub: connect, auto-commit, pull/push, branch switch, import a repo
- Deploy to a public URL, custom subdomain/domain, analytics, marketplace
- GitAgent (beta): agents as git repos (`SOUL.md`, `RULES.md`, skills, memory)
- Lyzr Studio for editing agents; MCP / custom tools; sharing with teammates
- Testing agent, env vars, artifacts, credit/usage dashboard
- Self-Correction / QA Loop: automatic error detection and code rewriting during builds

The “also serve developers” gap is things like repo import, GitAgent, code ownership, branches, and any-framework agents — Cursor/Replit-class power on top of the non-technical flow.
